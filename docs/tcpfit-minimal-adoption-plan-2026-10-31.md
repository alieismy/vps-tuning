## 1. 推荐范围

**本次仅实施“离线中文覆盖摘要”本地候选；其余运行能力继续复用或暂缓。** 它是减少报告阅读成本的可选增强，不是必须修复的正确性缺陷，也不承诺性能收益。如果使用反馈表明只是重复已有输出，没有减少人工对照工作，仍可撤回本项候选。

实施前核实的展示缺口：`dvt report` 已输出逐档分类和停止原因；原 `tools/explain_measurement.py` 已输出逐样本计数及候选高档观察，但不读取 `plan.json`，且仅在存在候选时给出高档观察。用户需要人工对照归档计划与实际样本，才能快速识别“计划有哪些扫描档、哪些形成足量有效样本、哪些缺失或不足”。新增摘要只补这层对应关系，不重建逐档报告、分类器或测量器。[现有解释器](../tools/explain_measurement.py)、[现有测量实现](../dvt-measure.py)

| 路线 | 预期收益与代价 | 本次选择 |
|---|---|---|
| A：不改代码，使用现有 report、解释器和计划文件 | 零新增维护成本；继续人工对照计划和样本 | 合法回退方案；现有输出足够时采用 |
| B：在现有解释器的中文输出中加入覆盖摘要 | 用已有证据减少人工对照；只增加本地读取、派生与展示 | **推荐的唯一当前代码候选**；不改变采集或系统状态 |
| C：增加 coverage JSON、集成主 CLI 或新建摘要工具 | 可服务新的程序化调用，但需扩大输出契约、集成与发布验证 | 当前没有调用者需求，暂缓；不为展示目的提前建设 |

选择 B 的置信度：技术可行性高，实际易用性收益中，须以输出前后对照确认。它不依赖 N1 多流试验，也不依赖迁移器或旧 TcpQuality 的原生验收。N1 同样不必等待摘要完成。

## 2. 当前候选改动：仅增加离线中文覆盖摘要

### 2.1 最小落点与输出边界

沿用 `tools/explain_measurement.py --input-dir ...` 的现有中文输出入口，在原状态、候选和逐样本解释附近增加简短摘要。只展示以下信息：

1. **归档计划中的扫描档位及每档期望样本数。** 用最终落盘计划中的 `schedule`，按 `role=sweep` 分组计数；明确这是归档计划，可能包含运行中已追加的细扫。
2. **逐档样本齐全且原报告认定有效的档位。** 同时对照该档计划、实际 sweep 样本与原汇总；不把这个标签写成整轮测量成功或网络容量已验证。
3. **尚未形成足量有效证据的档位。** 区分无样本、样本不足、含无效样本及资料缺失/不一致；显示离散档位，不用单个“最高已验证速率”掩盖中间缺口。
4. **原停止原因和原结论。** 复用已有输出，不重复另一套状态机。原报告为不足证据时，即使部分扫描档齐全，仍保留原结论。

数据依赖仅为已经通过 `verify_report()` 完成标记、摘要与恢复检查的 `plan.json`、`measurement-result.json` 中的 `samples` 和 `analysis.tested_rates`。`verify_report()` 当前会验证计划文件摘要，但返回值只有 result；在中文输出路径补充读取固定文件名的计划，不修改其返回接口或再做一套证据校验器。

**首版仅增强中文文本。** 不增加 `--coverage` 等新命令，不增加 `--json` 字段、不变更 `dvt.measurement-explanation/1` 或测量 schema，不把派生覆盖数据写回归档。现有 `explain(result)` 的原分析、计数与候选解释语义保持；摘要计算只服务文本展示，不另建模块、状态文件或缓存。

工具已发布为 0.1.0，新代码不能继续冒充该已发布制品。实施时建议采用独立工具本地候选标识 **`0.1.1-dev`**；`--json` 中只有 `tool_version` 随候选版本正常更新，既有字段集合和语义保持，不承诺新旧 JSON 逐字节相同。正式版本号、打包和发布以后单独决定；主程序 rc.4 及其资产不动。

### 2.2 必须保留的语义

- 计划字段只校验本次展示使用的类型、角色、速率与重复次数；不扩展成通用 schema validator。
- `control-start/control-end` 和 `reference-start/reference-end` 不计入 sweep 覆盖；其影响继续由原分析状态及 issues 表达，不另造总体“通过”判据。合法计划没有 sweep 时显示“无独立扫描档”，不输出 `0/0` 或“100% 覆盖”。
- HTB 的发送 cap 不等于扫描上界。不得用 `rate_cap_mbps`、`rates_mbps` 全列表或 `max_fine_rates` 猜测期望扫描；只采用最终 `schedule` 中实际登记的 sweep 项，未追加的潜在细扫不算缺失。
- 旧计划为空对象、使用字段不足或格式不支持时，只把新增摘要降级为“计划覆盖不可评估”，保留原解释能力和原退出语义。计划/样本/汇总矛盾时不补值、不取较乐观结果；明确资料不一致，不作完整覆盖判断。
- 上述降级不覆盖原完整性失败：摘要篡改、`INCOMPLETE`、缺失核心文件或 HTB 恢复证据不足仍按原入口拒绝。
- 离线只读，沿用冻结归档输入契约；不访问端点，不输出 IP、凭据或额外主机标识，不改源报告、账本、哈希或系统配置。

## 3. 当前改动的最小验收与退出

复用现有解释器测试，新增用例应证明以下行为，避免只检查打印了某个字符串：

| 场景 | 应证明的结果 |
|---|---|
| 完整扫描、有候选或无候选，以及合法计划无独立 sweep | 计划与实际档位对应正确；有无候选均可展示覆盖；无扫描档不冒充完整覆盖，原分类和候选不变 |
| 预算/时间停止、中间档样本不足或无效、没有可用对端 | 区分缺失与无效；不将最高出现档当连续覆盖；空样本不冒充完成 |
| HTB 归档含追加细扫、控制与 reference，发送 cap 高于扫描上界 | 只统计最终计划的 sweep，细扫不漏计，控制/reference 不混入，未追加细扫不算缺失 |
| 旧 `{}` 计划、缺失字段或计划/样本/汇总不一致 | 新摘要不可评估或明确不一致；不伪造零值或完整覆盖，不破坏旧 JSON 解释能力 |
| 篡改与恢复证据失败、冻结输入不变、机器输出兼容 | 原拒绝行为保留；源目录摘要不变；JSON 字段与语义保持，只有 tool_version 随候选更新 |

实现后先运行已有 `test_measurement_explanation.py` 全部用例，再做文档链接、编码和 diff 检查。已有可用的冻结真实报告可回读作前后对照；没有该材料时使用现有端到端 fixture，明确没有新增真实回读证据，不为补材料启动公网采集。若正式合入或发布进入范围，再执行该交付范围原本要求的门禁；本地文本候选不另加 root、VM、重启或公网性能矩阵。

完成标准：原先需要人工对照计划与样本的信息能在同一段摘要中看清，且以上语义成立、源证据与分类保持、无新增运行依赖。收益只有“读报告更容易”，不能写成测量准确率、性能或可靠 policer 识别提升。

退出条件：若前后对照只是重复现有逐档报告，或实现必须新增持久 schema/主 CLI/采集字段，则停止扩大该项，保留原工具与已有研究。未发布候选可整体撤回本项差异；不会产生服务器状态恢复问题，撤回时须保留当前其他未提交工作。

## 4. 继续暂缓的内容与重新进入条件

| 内容 | 现在为何不做 | 重新进入条件与最小动作 |
|---|---|---|
| N1：单流/多流自动配对或集成 | 1–4 流能力已存在；没有证据要求新增执行器、自动判据或入口 | 反复出现单流欠驱动或明确高速测量需求时，先在获授权环境复用 benchmark 做同总 cap 的 1/4 流交替对照；确认能改变诊断决策后，再考虑产品化 |
| N2：网络事件后 fq 保持性 | 未观察到当前缺陷；重启、链路 down/up、设备重建不能混用证据 | 实际 fq 漂移或新增平台支持要求出现时，只验证对应事件；不先增加所有网络管理器矩阵或持久 hooks |
| coverage JSON、主 CLI 集成或新工具 | 当前只发现文本阅读成本，没有机器调用需求 | 出现明确消费者且现有文本无法满足时，单独评估兼容/版本与集成成本 |
| 逐项调参预览、参数档案、fleet、PPP/initcwnd 持久化 | 增加受管面及恢复成本，当前无对应需求 | 用户明确使用场景后分别立项，不因上游具有该功能而纳入 |
| 新阈值、固定冷却/余量、更多 sysctl 或永久 HTB | 不能由上游经验直接推导本项目收益；涉及现有运行边界 | 有与本项目负载相关的可复现证据、明确需求和恢复路径时，再作独立决策；本计划不启动实验 |

N1 若被触发，沿用自检后的必要条件：匹配现有 benchmark 平台与依赖；显式设置 cap 与 `BENCHMARK_ENFORCE_RATE_CAP=1`；共享账本分别预留；固定 IP、端口、协议族、方向、时长、omit 和总 cap；记录两端版本、资源与实际路径，保留有效窗口和原始证据。无需为了测量先 apply 到 VERIFIED。单流欠驱动而多流达标可作为差异线索；两者均欠驱动或证据不充分时不自动扩预算、加流、抬 cap 或调参。同 cap 达标不等于测出更高容量。此处只保留条件，不新增运行脚本或测试命令手册。

## 5. 已有机制与实施授权边界

原子状态、共享预算、超时回收、无效证据拒绝、恢复核验、固定发布校验、公共端点选择与有限细扫已有对应机制。继续复用，不再以“吸收 tcpfit”为名建设第二套实现；只有映射到真实覆盖缺口的故障场景，才在原测试中补定向用例。

不直接采用上游的重传百分比强因果结论、可变 main 安装、校验降级、默认遥测和无预算的自动整形。这里区分的是当前项目契约，并非否定上游所有场景的有效性；默认 RTT、资源系数及本仓经验判据也没有被证明最优。

用户已明确要求“请按照方案实施代码”。本次授权落实为第 2 节的离线本地候选及第 3 节必要验证；不包括 N1/N2 执行、真实 VPS、公开发布、提交/推送、主程序升级或参数调整。实际实施状态以顶部状态和验证记录为准，其他推荐与重新进入条件继续保留。
