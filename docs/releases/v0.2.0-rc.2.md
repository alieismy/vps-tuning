## 修复范围

旧版本 verify 通过后，rc.1 的 schema 4 校验仍要求状态版本等于目标版本，导致只读 update-preflight 误拒绝。rc.2 在 `UPDATE_PREFLIGHT=1` 且动作是 `preflight` 时接受既定 `0.1.0-rc.1` 至 `rc.19` 来源的 schema 4；schema 3 的只读兼容保持。普通动作继续要求当前版本，所有其他动作在进入 root/锁与系统操作前拒绝该兼容标志。

保留单份 JSON、schema、profile、root 所有权、provider transfer 结构、受管路径及 APPLIED/VERIFIED 阶段门禁。普通模式版本不一致时给出来源与当前版本。控制器成功提示要求先完成目标 `migrate prepare`，不再直接提示执行旧版 rollback。

本版迁移目标为 `0.2.0-rc.2`；来源仍限定 `0.1.0-rc.1` 至 `rc.19`，没有新增 `0.2.0-rc.1` 来源、跨 OS 或 profile 切换。17 项 sysctl、BDP、预算、测量与临时 HTB 的实现和契约不变；未修改的独立工具保留原内部版本，由本次 manifest 固定其字节。

离线 probe 校准器增加 `0.2.0-rc.2` 版本标识的同格式兼容，并运行既有证据不变/结果一致回归；仍拒绝 adaptive profile，没有扩展测量 schema、策略或性能承诺。

## 恢复边界

`update` 是只读检查。两项 TCP 原值若各只有 `4096`，新预检可以通过，但普通迁移器必须继续拒绝创建 checkpoint。不能手改状态或用空状态 recover 绕过。具有完整历史三元组也不自动证明它属于当前部署；证据连续性与实际恢复必须分别验收，见[迁移指南](../migration.md)。

后续明确授权增加了源码工具 `tools/recover_tcp_baseline.py`：针对五组已知来源，保留原始 state，区分同部署历史证据和明确接受的新恢复基线，逐台绑定 VPS 编号、主机/状态/部署摘要与运行保护条件。prepare 只建立私有归档；activate 只改变两个缺失原值和来源字段；undo 只在未迁移且未漂移时恢复原 state。它不执行 rollback/apply/reboot，不是整机备份或已发布子命令。迁移器保存来源归档，在第一次重启后采集实际 TCP 基线并与目标 state 对照，详见[工具边界](../tcp-baseline-recovery.md)。新路径测试结果须独立绑定后续提交，不能套用首个预检修复提交的七平台 CI 结论。

该扩展实现提交 `3616444921d0bf688ee79e11f5816f0e41ef1485` 的[主 CI](https://github.com/alieismy/debian-vps-tuning/actions/runs/37178357578)已通过，20 项 Linux root 恢复专项无跳过，含历史/替代两种文件事务接迁移 CLI；四组 x86_64 VM 归档也已独立核验，三组 ARM64 尚在运行。上述结果不证明五台存量 VPS 已完成恢复或升级。

2026-10-05 后续结果：[平台 CI 37178357544](https://github.com/alieismy/debian-vps-tuning/actions/runs/37178357544) 七组全部成功，七份归档的 GitHub digest、VERIFIED 状态、两次客体重启、17 项 sysctl 及 qdisc 恢复均已独立核验。四台存量 VPS 的只读 inspect、固定来源验证与候选预检通过，另一台仍受自动化 SSH 认证限制；生产恢复与迁移尚未执行。详细证据层级见[验证说明](../validation.md)。
