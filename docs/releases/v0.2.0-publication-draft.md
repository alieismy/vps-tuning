## Release 正文待发布稿

v0.2.0 将首次正式版范围收敛到可验证、可恢复的主机网络配置与明确的 RC 迁移。保留 17 项受管 sysctl、资源感知缓冲、默认 BBR + fq、managed-state schema 4，以及已有诊断、预算约束测量和临时 HTB 能力；不增加永久整形或通用 UDP 调优。

迁移使用 schema 2 checkpoint，冻结带宽、RTT、缓冲、swap 与服务验证意图，保留固定来源、目标与恢复材料，经过两次人工重启和最终严格验证后才切换入口。来源必需范围为公开 rc.4/rc.5、Debian 12/13 同 profile、配置输入 1–10000 Mbps。rc.6 来源代码保留但未公开、未完成该来源端到端验收；Ubuntu/ARM64 迁移不新增承诺。旧 schema 1 checkpoint 和历史恢复归档继续使用自己的固定工具，不原地转换。

新装平台为 Debian 12/13、Ubuntu 24.04 LTS，x86_64/aarch64、原生 systemd，至少 1 个逻辑 CPU / 384 MiB RAM，仍须通过实际 BBR/fq、资源和可恢复队列预检。adaptive 不按最大 CPU/RAM 档位拒绝，4 vCPU、4 GB RAM 和 2000 Mbps 配置输入不因数值本身被排除；这不代表已验证 2 Gbps 实际吞吐、全部云内核或所有业务组合。Ubuntu 26.04 留待后继版本。

冻结实现的 Linux 主 CI、七组新装和四组真实来源隔离迁移已通过；首台 Lightsail 的 rc.4 adaptive / 无 swap 实机迁移和技术验证完成。**发布前仍须用已签收回执替换此状态：G4 客户端业务与 G5 至少 30 分钟正常使用观察待确认。** 不将服务核验或有限观察表述为全平台生产验证、性能收益或长期稳定性证明。

恢复边界：原值不完整时拒绝迁移；不猜默认值补写。目标 rollback 恢复原基线，不自动安装旧版本或回退 checkpoint。后期退出目标后的接续须遵循[实施契约](../stable-migration-design.md)；不手改 phase/active。正常业务机不承担故障注入，逐台生产变更须另行授权。

固定制品及工程证据见[候选说明](v0.2.0.md)和[验证记录](../validation.md#stable-020-freeze)。已公开 RC tag、Release 和资产保持不变。离线解释工具保持独立版本，不随本次安装更新。

## 发布后安装块（当前不要执行）

适用于 root shell 下的全新安装，或既有迁移已经 COMPLETE 的入口切换；不是旧 managed state 的就地覆盖办法。依赖与完整操作入口见[操作指南](../usage.md#执行前准备)。中英文 README 使用同一命令块：

```bash
(
  set -Eeuo pipefail
  test "$(id -u)" -eq 0
  dvt_i="$(mktemp)"
  trap 'rm -f -- "$dvt_i"' EXIT
  curl --fail --show-error --silent --location \
    --proto '=https' --proto-redir '=https' \
    --connect-timeout 15 --max-time 120 \
    -o "$dvt_i" \
    https://github.com/alieismy/vps-tuning/releases/download/v0.2.0/install.sh
  printf '%s  %s\n' \
    'b062c3031046d9d0c989e8efcc4b436872b00e5d94f966a9210e64b39d21ab78' \
    "$dvt_i" | sha256sum -c -
  bash "$dvt_i" --no-launch
  test "$(/usr/local/bin/dvt --version)" = 'controller=0.2.0 release=v0.2.0'
)
```

安装器校验固定 manifest 及全部运行文件；`--no-launch` 不执行调优或测速。非零退出即停止，不回退到可变分支、latest 或未经校验的入口。存在同版本但不同内容时不得绕过安装器冲突检查。

## 发布后迁移说明（分阶段，不是本轮执行指令）

以下是正式版本的顺序与停止条件，替换当前迁移指南顶部的 RC 目标说明；历史 RC 命令保留在标明版本的历史章节。已经 COMPLETE 的首台主机不得重跑此流程。

1. 确认真实来源为 rc.4/rc.5、Debian 12/13、同 profile，来源严格核验与原值完整；检查现存活动 checkpoint。确认恢复点、离机 DVT 证据、控制台救援、业务基线、维护预算和逐台授权。已有未完成事务先接续原事务，不能重新 prepare。
2. 发布后可用现有入口 `dvt update --target v0.2.0` 做只读升级检查；它仅生成计划，不安装或迁移。目标已是 0.2.0 的主机不以同版 update 代替来源迁移验证。旧入口无法覆盖的输入限制应按目标工具契约处理，不绕过来源与恢复门禁。
3. 从发布清单中固定的 26 项资产准备树外完整 bundle，按清单仓库路径还原子目录；验证独立固定的安装器与 manifest 摘要，再执行 `sha256sum -c SHA256SUMS`。目录及文件须 root 所有、不可被其他用户写入。此时不安装新入口。包准备不等于完全离线：prepare 仍会解析公开固定来源资产。
4. 在已校验 bundle 中调用目标总控 `bash debian-vps-tuning.sh migrate prepare --checkpoint /absolute/new/path`。checkpoint 必须为新的绝对路径，位于受管状态树外。已有项目 swap 自动保留；未创建项目 swap 时明确追加 `--swap-policy disabled`，或经批准追加 `--swap-policy create --swap-mib N`（N 是批准的 MiB 数，执行前填写）。自定义服务用 `--proxy-unit UNIT`；未指定且发现已加载 x-ui.service 时会绑定它。prepare 写入 checkpoint 和活动登记，不写系统调优配置。
5. 仅当状态为 PREPARED，核对并离机保留 intent/摘要后，使用该 checkpoint 内的固定 `dvt-migrate.sh rollback --checkpoint /absolute/new/path`。到达 ROLLED_BACK_REBOOT_REQUIRED 后停止，由操作者按已批准安排人工重启。
6. 重连核对 boot ID 改变、恢复基线与管理可达性后，用同一个固定工具执行 `continue --checkpoint /absolute/new/path`。目标 apply 达到 TARGET_APPLIED_REBOOT_REQUIRED 后停止，安排第二次人工重启；不提前切换入口。
7. 再次核对新 boot ID，用同一固定工具再次 continue，严格验证到 COMPLETE。之后才运行上面的固定安装块，并独立核验入口版本、目标 state 与严格服务状态；绑定服务的核验方式沿用[首台执行契约](../first-host-migration-acceptance.md)。最后另行完成客户端业务与正常使用观察。

每段失败或 phase 不符即停止。prepare 仅在 PREPARED 可 cancel；半成品、状态漂移、APPLIED 残留或后期目标退出按[迁移恢复契约](../stable-migration-design.md)与[恢复分支](../first-host-migration-acceptance.md)处理。不要删除 active、手改 checkpoint、重复 apply 或以重启服务代替整机重启。快照恢复到新 Lightsail 实例涉及 Static IP 重新绑定等云操作，只能由另行获授权的恢复流程执行；本次不实施或演练。
